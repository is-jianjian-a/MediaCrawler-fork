# 小红书抓取速率基线与风控处置

更新日期：2026-08-29

这份文档固化本仓库历史任务的经验，用于 Dashboard 新建任务的默认值。它是**当前账号、网络、实现和样本下的操作基线**，不是小红书公开限额，也不是可以持续逼近的硬阈值。

## 默认策略

| 场景 | 并发 | 帖子详情随机等待 | 评论帖间隔 | 一级评论上限 | 二级评论 | 批次间隔 |
|---|---:|---:|---:|---:|---|---:|
| 关键词纯抓帖 | 1 | 45–65 秒 | 不适用 | 不抓 | 关闭 | 不适用 |
| 关键词抓帖 + 一级评论 | 1 | 60–75 秒 | ≥90 秒 | ≤5 条/帖 | 关闭 | 不适用 |
| 高价值帖子评论补抓 | 1 | 60–75 秒 | ≥90 秒 | ≤5 条/帖、≤2 帖/任务 | 关闭 | 60 秒/批 |
| 461/471 后恢复探针 | 1 | 240–300 秒 | 不抓评论 | 不抓 | 关闭 | 不适用 |

实现口径：

- `详情随机等待` 由 `MEDIACRAWLER_CRAWLER_MIN_SLEEP_SEC` 和 `MEDIACRAWLER_CRAWLER_MAX_SLEEP_SEC` 控制。
- 现有 `smart_sleep()` 会在配置区间采样后叠加高斯抖动，只保证不低于下限，偶尔可能高于名义上限；因此 45–65、60–75 是配置档名，不是每一次睡眠的严格边界。
- `评论帖间隔` 由 `MEDIACRAWLER_CRAWLER_COMMENT_SLEEP_SEC` 控制，指一篇帖子评论任务结束到下一篇之间的等待，**不是逐条评论间隔**。
- 一级评论分页之间仍有代码内的 3 秒等待；一次评论任务还会先刷新一次帖子详情，因此不能把 `comment_sleep` 当成真实 HTTP 请求间隔。
- 二级评论是明显更重的独立路径；默认关闭，不能套用一级评论对象速率估算。

## 历史观测

完成的关键词任务中：

- 45–65 秒配置组（11 个进程完成任务）：新帖子约 0.42–0.86 条/分钟（P25–中位数），总处理帖子中位数约 1.01 条/分钟，应用日志记录的 API 约 0.029–0.038 次/秒（P25–中位数）。其中包含下文发生 461 后仍被旧实现记为完成的评论重任务，因此“进程完成”不等于无风控；45–65 只用作纯抓帖默认，不据此认定混合评论任务安全。
- 20–40 秒组（5 个完成任务）：新帖子约 1.09–1.35 条/分钟，应用日志 API 约 0.047–0.063 次/秒。它能跑完部分任务，但只保留为小样本短测档，不作为长期默认。
- 单次 10–20 秒、无评论任务观测到 5.57 个新帖/分钟、0.337 次应用日志 API/秒。只有 1 个样本，不能作为安全上限。

完成的一级评论补抓任务中，3 个采用 60–75 秒详情等待、30 秒评论帖间隔的任务合计处理 33 帖、写入 654 条评论，用时约 58.7 分钟且无失败；对象速率约 0.56 帖/分钟、11.1 条入库评论/分钟。这是入库对象速率，不是 HTTP 请求速率。

## 461/CAPTCHA 风险样本

`dashboard/logs/crawl-030f42fa.log` 的长任务使用并发 1、详情等待 45–65 秒、评论帖间隔 5 秒。在启动约 146 分 43 秒后出现第一次 HTTP 461；此前已启动 118 次初始详情请求和 188 个评论任务。评论任务本身包含详情刷新与评论分页，首个 461 发生在第 189 个评论任务的详情刷新阶段。

历史实现对每个 461 重试 3 次，又在评论详情刷新处吞掉最终异常，所以出现 6 组、共 18 次 CAPTCHA 后仍继续运行并最终被标记为完成。这个样本说明：

- 风险更像持续会话中的“详情刷新 + 评论分页”组合压力，不能只看一个 sleep 参数。
- 单账号、单会话不足以推出精确 API/s 限流线，账号状态、IP、内容和历史活动均为混杂因素。
- 任何明确的 HTTP 461/471 都应立即停止当前任务，不再重试；等待人工完成验证或切换到恢复档后再重新启动。

当前代码已把 461/471 转为终止型 `RiskControlError`，并使用专用退出码 75。该异常不得被单帖容错吞掉；同批并行请求会被取消，评论补抓的后续批次也不会再启动。Dashboard 应把关键词任务显示为失败，把评论补抓任务显示为完成但有错误，并保留未抓帖子的风控停止原因。

## 账号级状态机（Dashboard 搜索与评论共享）

`dashboard/risk_policy.py` 将同一账号的搜索任务和评论任务放在同一个持久化预算里；不同注册账号拥有互不累计的状态。状态写入 `~/Library/Application Support/MediaCrawler/database/task_manager.db`，Dashboard 或 worker 重启后不会清零。多账号的 Profile、内容库、日志、调度和故障边界见 [小红书多账号隔离并行运行](xhs_multi_account_isolation.md)。

| 状态 | 含义 | 自动动作 |
|---|---|---|
| `normal` | 已通过恢复检查 | 允许符合范围的搜索或评论任务 |
| `cooldown` | 第一次 461/471 后 | 冷却 4 小时，拒绝所有新启动 |
| `canary` | 冷却结束、尚未完成两次干净探针 | 自动把下一条排队搜索收紧为最多 5 帖、无评论、并发 1、详情等待 240–300 秒，浏览器就绪后等待 75 秒再首搜 |
| `locked` | 同一自然日第二次 461/471 | 当天停止全部自动化，次日才进入恢复探针 |

全状态通用预算：

- 任一任务完成后至少间隔 60 分钟。
- 两次浏览器启动至少间隔 90 分钟。
- 任意滚动 12 小时最多启动 16 个浏览器任务会话。该值取自历史无显式风控的滚动 12 小时峰值 20 次，保留 20% 余量；它是内部策略值，不是平台公开限额。

注意：当前 standard mode 每个 Dashboard worker 都有独立的 Playwright 生命周期，任务结束时会清理自己的 browser context。即使把 `AUTO_CLOSE_BROWSER` 设为 false，也不能在 worker 进程退出后安全地跨任务复用浏览器，反而可能留下占用 Profile 的孤儿进程。因此这里计数的是“浏览器任务会话”；减少重复开关应优先靠合并搜索工作、聚合评论候选后再跑一个批次。

- 为避免搜索/评论任务交替反复开浏览器，账号闸门要求一个评论会话之后至少累计 2 个新搜索会话，才允许开启下一个合并评论批次。
- 评论只有在两次干净搜索探针完成后才能启动；每次最多 2 帖、每帖最多 5 条、评论间隔至少 90 秒。
- 不自动切换账号、代理、浏览器指纹；Dashboard 任务禁用 CDP、端口 9222 和系统 Chrome。
- CAPTCHA 不能自动解决。无人值守的含义是系统会安全停机、等待、探针恢复；仍需验证码时保持暂停，不伪装成持续采集成功。

Dashboard 后台每 30 秒检查一次 `start_mode=auto` 的待处理队列。被冷却或启动预算拒绝的任务保持 `pending`，到达允许时间后自动再次评估；失败任务不会原地自动重试。搜索优先于评论，以保证恢复探针先完成。同一账号严格串行；一个账号被拒绝不会阻塞其他账号，默认最多 4 个隔离账号并行。

## 操作规则

1. 长任务默认使用上表基线；不要因为某个短任务成功就提高长期默认值。
2. 首轮搜索优先只抓帖子，再从高价值帖子创建评论补抓任务，避免在一个长会话叠加所有请求路径。
3. 出现 461/471 后立即停，不自动换账号、换 IP 或连续重启。第一次进入 4 小时冷却；同日第二次熔断到次日。
4. 冷却结束后必须完成两次 1–5 帖搜索探针；探针由执行层自动收紧，不能带评论。两次均干净完成后才恢复普通 10–14 帖样本和独立小评论任务。
5. 评估速率时区分：新写入帖子、总处理帖子、入库评论、应用记录 API、真实 HTTP 请求。它们不能互相替代。

## 证据位置与限制

- 关键词任务：`dashboard/logs/crawl-*.log`，以日志起止墙钟、搜索页累计和任务末尾 API 摘要计算。
- 评论补抓任务：`~/Library/Application Support/MediaCrawler/database/task_manager.db` 的任务起止、帖子和评论写入字段。
- 风控事件：`dashboard/logs/crawl-030f42fa.log` 第 2196–2249 行附近。
- 风控台账：`database/risk_control_log.md`。

应用的 API 摘要没有覆盖评论 worker 的全部详情刷新和分页请求，因此不能当成真实网络请求总数；数据库 `add_ts` 也可能混入并行任务，不能直接用于单任务速率。
